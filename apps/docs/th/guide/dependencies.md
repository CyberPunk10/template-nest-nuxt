# การอัปเดต dependency

เวอร์ชันของแพ็กเกจถูกบันทึกไว้สองที่: ช่วงเวอร์ชัน (`^11.2.8`) อยู่ใน `package.json` ของแต่ละแพ็กเกจใน workspace และเวอร์ชันที่ติดตั้งจริงของทั้ง tree อยู่ใน `pnpm-lock.yaml` การอัปเดตคือการเปลี่ยนทั้งสองไฟล์อย่างตั้งใจ ซึ่งเห็นได้ใน diff และผ่านการตรวจสอบเดียวกับโค้ดอื่น ๆ

## 1. ดูว่าอะไรล้าสมัย

```bash
pnpm outdated -r
```

แสดงเวอร์ชันที่ติดตั้งและเวอร์ชันล่าสุดที่เผยแพร่ ของทุกแพ็กเกจใน workspace

## 2. อัปเดตภายในช่วงเวอร์ชัน

```bash
pnpm update -r    # เหมือนกับสคริปต์ pnpm deps:sync
```

`-r` หมายถึงทุกแพ็กเกจใน workspace คำสั่งนี้อัปเดตแพ็กเกจเป็นเวอร์ชันล่าสุดที่ช่วงเวอร์ชันอนุญาต และเขียนค่าใหม่ลงใน `package.json` lockfile จะถูกเพิ่มเติม ไม่ได้คำนวณใหม่ทั้งหมด สำหรับ `^` คือเวอร์ชัน minor และ patch สำหรับ `~` คือเฉพาะ patch

pnpm จะไม่ดึงเวอร์ชันที่เผยแพร่มาไม่ถึงหนึ่งวัน — เป็นการป้องกันการโจมตีผ่านแพ็กเกจใหม่: เวอร์ชันที่ถูกเจาะมักถูกตรวจพบและถอดออกภายในหนึ่งวัน ดังนั้นรีลีสที่เพิ่งออกจะถูกดึงมาในวันถัดไป เกณฑ์นี้กำหนดด้วยการตั้งค่า [`minimumReleaseAge`](https://pnpm.io/settings#minimumreleaseage) ใน `pnpm-workspace.yaml` หน่วยเป็นนาที

อัปเดตแพ็กเกจเดียว:

```bash
pnpm update -r vue
```

## 3. เวอร์ชัน major — ทีละตัว

เวอร์ชัน major อยู่นอกช่วงเวอร์ชันและอาจทำให้ API เสีย จึงควรอัปเดตแยกจากตัวอื่นและทีละแพ็กเกจ:

```bash
pnpm update -r --latest --interactive
```

คำสั่งจะแสดงรายการอัปเดตที่มีและให้เลือกตัวที่ต้องการ ก่อนอัปเดต major ให้อ่าน release notes หรือ migration guide ของแพ็กเกจ

## 4. ตรวจสอบ

รัน linter, ตรวจ type, build และเทสต์:

```bash
pnpm lint
pnpm type-check
pnpm build
pnpm test
pnpm test:e2e
```

## ตรึงเวอร์ชันไว้

ถ้าเวอร์ชันใหม่ของแพ็กเกจเสีย ให้เปลี่ยน `^` เป็น `~` — แล้ว `pnpm update -r` จะดึงเฉพาะเวอร์ชัน patch และไม่ดึง minor ที่เสียเข้ามา ใน commit message ให้ระบุเหตุผลและเงื่อนไขที่จะเปลี่ยนกลับเป็น `^` เช่น ลิงก์ไปยัง issue

## อัปเดต pnpm

```bash
pnpm self-update
```

ในโปรเจกต์ คำสั่งนี้เปลี่ยนเฉพาะเวอร์ชันใน `packageManager` ของ `package.json` ที่ root และไม่แตะ pnpm ที่ติดตั้งแบบ global commit `package.json` พร้อมกับ `pnpm-lock.yaml` — pnpm ของนักพัฒนาคนอื่นจะสลับไปใช้เวอร์ชันใหม่เองในการรันครั้งแรก

## ช่องโหว่

```bash
pnpm audit
```

ช่องโหว่บางส่วนอยู่ลึกใน transitive dependency ของเครื่องมือ build และแก้ไม่ได้ด้วยการอัปเดตฝั่งคุณ ให้ดูที่เส้นทาง (`Paths`): ช่องโหว่ในแพ็กเกจที่เข้าไปอยู่ใน production build สำคัญกว่าในเครื่องมือสำหรับ dev

## ติดตั้งใหม่ทั้งหมดตั้งแต่ต้น

```bash
pnpm reinstall
```

[`pnpm reinstall`](./structure/scripts/reinstall) ไม่ใช่วิธีอัปเดต แต่เป็นทางเลือกสุดท้ายเมื่อ dependency ในเครื่องเสียและวิธีอื่นไม่ได้ผล

::: warning
คำสั่งนี้ลบ `node_modules` และ lockfile ทั้งหมดแล้วติดตั้งใหม่ตั้งแต่ต้น: transitive dependency ทั้งหมดจะถูกดึงเวอร์ชันใหม่พร้อมกัน และบางอย่างในโปรเจกต์อาจเสียจนต้องหาสาเหตุและแก้ไข ตรวจสอบ diff ของ `pnpm-lock.yaml` ทุกครั้งก่อน commit
:::
