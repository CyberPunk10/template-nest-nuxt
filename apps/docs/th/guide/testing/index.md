# การทดสอบ

เทสต์อยู่ภายใน application ที่มันตรวจสอบ: แต่ละ package ใน workspace มี runner ของตัวเอง มี config ของตัวเอง และมี dependency ของตัวเอง ไม่มี test package กลางในโมโนรีโป — application ที่เป็น NestJS กับ Nuxt ทดสอบคนละแบบ และ config กลางก็คงต้องแตกเงื่อนไขตามความต่างทุกจุด

จาก root ของโมโนรีโป จุดเริ่มยังเป็นคำสั่งเดียว:

```bash
pnpm test         # unit test ทุก package
pnpm test:e2e     # e2e test ทุก package
```

ทั้งสองคำสั่งรัน `pnpm -r` คือไล่ไปทุก package ใน workspace แล้วเรียก script ชื่อเดียวกัน package ที่ไม่มี script นั้นจะถูกข้ามไปเงียบ ๆ — การเพิ่มเทสต์ให้ application ใหม่ก็แค่เพิ่ม script `test` ใน `package.json` ของมัน โดยไม่ต้องแก้อะไรที่ root

จะจำกัดให้รันแค่ package เดียวโดยไม่ต้องเข้าไปในโฟลเดอร์ก็ได้ ด้วย `--filter`:

```bash
pnpm --filter @repo/backend test           # unit test ของ backend เท่านั้น
pnpm --filter @repo/backend test:e2e       # e2e test ของ backend เท่านั้น
pnpm --filter @repo/backend test:watch     # script ใดก็ได้ของ package นี้
```

`--filter` รับชื่อ package จาก `package.json` ของมัน ชื่อเต็มย่อได้ (`backend`) หรือใช้ path แทนก็ได้ (`./apps/backend`) argument ที่ตามหลังชื่อ script จะถูกส่งต่อไปตรง ๆ ดังนั้น flag ของ runner ใช้จากตรงนี้ได้เหมือนกัน

มีจุดหนึ่งที่ควรรู้ไว้: ถ้า package ที่เลือกไม่มี script ที่ขอ pnpm จะจบการทำงาน **ด้วย exit code 0 และไม่มี output** จะไม่มี error — ใน CI การรันแบบนี้เข้าใจผิดว่าสำเร็จได้ง่าย ทั้งที่ไม่มีอะไรถูกรันเลย

## สองระดับ

การแบ่งเป็น unit กับ e2e ใช้ทั่วทั้ง repository ไม่ว่าจะใช้ runner ตัวไหน

**Unit test** ตรวจโค้ดหน่วยเดียวแบบแยกเดี่ยว: dependency ถูกแทนด้วย stub และไม่มีอะไรอื่นถูกยกขึ้นมา รันเร็ว — นับเป็นมิลลิวินาที จึงเหมาะกับการเปิด watch mode ค้างไว้ระหว่างทำงาน

**E2E test** ตรวจ application ที่ประกอบเสร็จแล้วทั้งก้อน โดยเข้าถึงจากภายนอกแบบเดียวกับที่ client จริงทำ

การแบ่งนี้ไม่ใช่แค่พิธีการ: สองระดับนี้ต่างกันที่ขอบเขตของความผิดพลาดที่มันจับได้ unit test ตอบว่า «ฟังก์ชันนี้ทำงานถูกไหม» ส่วน e2e ตอบว่า «application ประกอบขึ้นมาถูกไหม» ความผิดพลาดในการต่อสายระหว่างเลเยอร์ — global setting ที่ไม่ได้ถูกลงทะเบียน, contract ระหว่างโมดูลที่เคลื่อนออกจากกัน — ระดับแรกมองไม่เห็นเลยโดยหลักการ เพราะแต่ละส่วนแยกกันแล้วถูกต้องหมด

ดังนั้น e2e ไม่ได้แทน unit test และก็ไม่ได้ถูกแทนด้วย unit test เช่นกัน unit test ครอบคลุมลอจิกที่มีการแตกเงื่อนไข ส่วน e2e ครอบคลุม contract ของ application ที่ยื่นออกไปข้างนอก การไปไล่ทำซ้ำทุกเงื่อนไขในระดับที่ช้ากว่าไม่มีประโยชน์

## ข้อตกลงร่วม {#conventions}

ใช้ร่วมกันทุก application ในเทมเพลต:

- **Unit test วางไว้ข้างไฟล์ที่มันตรวจ** ต่างกันที่ suffix: `foo.ts` → `foo.spec.ts` แบบนี้เทสต์จะไม่หายไปตอนย้ายโมดูล และเห็นได้ทันทีใน tree ของโปรเจกต์
- **E2E test แยกไปไว้อีกโฟลเดอร์** ของ application: มันไม่ได้ผูกกับไฟล์ใดไฟล์หนึ่ง แต่ผูกกับ application ทั้งก้อน
- **ทุกเทสต์เริ่มจาก state ที่สะอาด** เทสต์ที่ขึ้นกับลำดับการรันจะเริ่มพังทีละตัวเมื่อสลับลำดับหรือรันขนานกัน — และ runner สลับลำดับไฟล์ได้อิสระ
- **เทสต์ต้องทำงานกับ object แบบเดียวกับที่ application จะได้รับจริง** stub ที่ง่ายเกินไป หรือ literal ที่ใช้แทนโครงสร้างข้อมูลจริง ให้ผลเป็นเทสต์สีเขียวบนเส้นทางที่ไม่มีอยู่ใน application

## เรื่องที่ควรจำไว้ {#worth-keeping-in-mind}

Coverage เป็นตัวชี้แนว ไม่ใช่เป้าหมาย บรรทัดที่เทสต์รันผ่านแต่ไม่ได้ตรวจผลลัพธ์ก็ยังนับว่า covered ดังนั้นเปอร์เซ็นต์สูง ๆ เพียงอย่างเดียวไม่ได้รับประกันอะไร

วิธีที่เชื่อถือได้กว่าคือทดสอบด้วยการ mutate: ใส่ความผิดพลาดลงในโค้ดแล้วดูว่าเทสต์กลายเป็นสีแดงจริงไหม เทสต์ที่ยังเขียวอยู่บนโค้ดที่พังแล้วไม่ได้ตรวจอะไรเลย — และแย่กว่าไม่มีเทสต์ เพราะมันสร้างความรู้สึกปลอดภัยที่ไม่จริง
