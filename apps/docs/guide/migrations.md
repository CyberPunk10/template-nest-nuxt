# Миграции

Миграция — SQL-файл, который переводит БД из одного состояния схемы в следующее. Миграции создаёт и применяет [Prisma Migrate](https://www.prisma.io/docs/orm/v7/prisma-migrate). Здесь — как это устроено в шаблоне и что делать в типичных ситуациях.

## Шпаргалка

Команды `pnpm prisma ...` выполняются из `apps/backend/`, команды `pnpm db:*` — из корня.

| Задача                                   | Команда                                                               |
| ---------------------------------------- | --------------------------------------------------------------------- |
| Создать и применить миграцию             | `pnpm prisma migrate dev --name <имя>`                                |
| Создать миграцию для правки, не применяя | `pnpm prisma migrate dev --name <имя> --create-only`                  |
| Применить новые миграции                 | `pnpm db:migrate`                                                     |
| Перегенерировать клиент                  | `pnpm db:generate`                                                    |
| Что применено, что нет                   | `pnpm prisma migrate status`                                          |
| Отметить упавшую миграцию                | `pnpm prisma migrate resolve --rolled-back <имя>` / `--applied <имя>` |
| Пересоздать локальную БД                 | `pnpm prisma migrate reset`, затем `pnpm prisma db seed`              |

## Как устроено

Файлы лежат в `apps/backend/`, журнал — в самой БД:

| Что                         | Где                               | Роль                                                               |
| --------------------------- | --------------------------------- | ------------------------------------------------------------------ |
| Схема                       | `prisma/schema.prisma`            | Какой должна быть БД. Правится только она                          |
| История миграций            | `prisma/migrations/`              | По папке с `migration.sql` на каждое изменение. Коммитится целиком |
| Журнал применённых миграций | таблица `_prisma_migrations` в БД | Какие миграции уже применены и с какой контрольной суммой          |
| Клиент Prisma               | `src/generated/prisma`            | Строится из схемы, в репозитории его нет                           |

Схема и история — два разных источника. В БД попадает только история: `migrate deploy` применяет файлы из `prisma/migrations/` и схему не читает. Клиент, наоборот, строится из схемы и о миграциях ничего не знает. Поэтому после изменения схемы нужны оба шага: миграция для БД и генерация для клиента.

`prisma/migrations/migration_lock.toml` тоже коммитится: по нему Prisma замечает попытку сменить СУБД.

## Когда миграции применяются автоматически

Проект настроен так, что миграции применяются сами при каждом запуске — вручную их применять не нужно:

| Запуск           | Кто применяет                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm dev`       | `predev.mjs`, шаг `migrations` — [подробнее](/guide/structure/scripts/predev)                                                     |
| `pnpm docker:up` | контейнер backend при старте, до запуска приложения — [подробнее](/guide/structure/apps/backend/docker-image#миграции-при-старте) |

В обоих случаях это `prisma migrate deploy`. Он применяет только миграции, которых ещё нет в БД, ничего не спрашивает, не создаёт новых миграций и не пересоздаёт БД. Уже применённые миграции он пропускает, поэтому повторный запуск ничего не меняет. При этом он выполняет `migration.sql` как есть и не предупреждает о потере данных — поэтому SQL проверяют до коммита.

`prisma migrate dev` — инструмент того, кто меняет схему: он создаёт новые миграции и может предложить пересоздать БД. Его запускают только вручную.

## От правки схемы до продакшена

Полный цикл изменения схемы. Главное правило: на продакшене `migrate deploy` выполнит `migration.sql` как есть, без вопросов, поэтому всё, что защищает данные, делается **до коммита** и **до выкатки**.

### Разработка

БД должна быть поднята — её поднимает `pnpm dev` или `pnpm db:up`. Команды `pnpm prisma ...` выполняются из `apps/backend/`.

1. **Поправьте схему** — `prisma/schema.prisma`.

2. **Создайте миграцию, не применяя её:**

   ```bash
   pnpm prisma migrate dev --name add_task_priority --create-only
   ```

   Появится `prisma/migrations/<дата>_add_task_priority/migration.sql`. Имя — коротко о сути изменения, в `snake_case`. Если изменение только добавляет новое (таблицу, необязательное поле), `--create-only` можно не указывать: миграция сразу применится, шаг 4 пропускается.

3. **Прочитайте `migration.sql`.** Особенно внимательно — к строкам, которые могут потерять данные или упасть на заполненной таблице:

   | В SQL                                    | Чем опасно                                   | Что делать                                                                       |
   | ---------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------- |
   | `DROP COLUMN`, `DROP TABLE`              | данные удаляются                             | если это переименование — [заменить на `RENAME`](#переименование-поля-или-модели) |
   | `ADD COLUMN ... NOT NULL` без `DEFAULT`  | миграция упадёт, если в таблице есть строки  | [задать значение по умолчанию или разбить на шаги](#обязательное-поле-в-таблице-с-данными) |
   | `ALTER COLUMN ... TYPE`                  | упадёт или исказит значения, которые не приводятся к новому типу | проверить на данных, при необходимости добавить `USING`             |
   | `CREATE UNIQUE INDEX`                    | упадёт, если в данных уже есть дубликаты     | сначала убрать дубликаты отдельным `UPDATE`/`DELETE` в той же миграции           |

   Prisma и сама предупреждает о потере данных — комментарием в начале `migration.sql` и в выводе `migrate dev`.

4. **Примените миграцию:**

   ```bash
   pnpm prisma migrate dev
   ```

5. **Проверьте результат.** Повторный `pnpm prisma migrate dev` должен ответить `Already in sync, no schema change or pending migration was found.` — значит, SQL привёл БД ровно к схеме. Если Prisma предлагает новую миграцию, правка в шаге 3 неверна. Данные Prisma не проверяет: если меняли таблицу с данными, заранее положите в неё тестовые строки и после применения убедитесь, что они на месте (`pnpm prisma studio`).

6. **Обновите клиент** и код, который использует изменённые поля:

   ```bash
   pnpm prisma generate   # из корня — pnpm db:generate
   ```

7. **Закоммитьте схему и папку миграции вместе**, одним коммитом. На ревью `migration.sql` читают так же внимательно, как код.

::: info Теневая БД
Перед созданием миграции `migrate dev` прогоняет всю историю на временной «теневой» БД, чтобы убедиться, что история и реальная БД сходятся. Для этого пользователю БД нужно право создавать базы. У пользователя из `docker-compose.yml` оно есть: образ Postgres создаёт `POSTGRES_USER` суперпользователем.
:::

### Продакшен

1. **Проверьте миграцию на копии продовых данных**, если она меняет таблицы с данными. Локальная БД обычно маленькая и чистая, а на проде бывают `NULL`, дубликаты и значения, о которых вы не знаете. Восстановите свежую копию продовой БД (staging или дамп, снятый как в шаге 2) и примените к ней `migrate deploy`.

2. **Сделайте резервную копию** продовой БД перед выкаткой — из папки проекта на сервере:

   ```bash
   docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > backup.dump
   ```

   Восстановить из неё:

   ```bash
   docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backup.dump
   ```

3. **Выкатите новую версию.** Миграции применит сам контейнер backend при старте — до запуска нового кода, через `migrate deploy`. Запускать что-то вручную не нужно.

4. **Если старая версия приложения продолжает работать во время выкатки** — несколько экземпляров, постепенная выкатка — ломающее изменение нужно разбить на совместимые шаги: [expand and contract](#без-простоя-expand-and-contract).

5. **Если миграция упала**, контейнер backend не запустится, причина — в его логах (`docker compose logs backend`). Что делать дальше — в разделе [Миграция упала](#миграция-упала), вариант «если данные нужно сохранить».

На продакшене никогда не запускают `migrate dev`, `migrate reset` и `db push`: первые два могут пересоздать БД, а `db push` меняет её в обход истории миграций.

## После `git pull`

Ничего делать не нужно: `pnpm dev` перед стартом сгенерирует клиент и применит новые миграции.

Если приложения уже запущены, перезапустите `pnpm dev` или выполните шаги вручную (БД должна быть поднята):

```bash
# из корня
pnpm db:generate   # в apps/backend — pnpm prisma generate
pnpm db:migrate    # в apps/backend — pnpm prisma migrate deploy
```

## Ломающие изменения

Править `migration.sql` безопасно, пока миграция не применена. Поэтому её создают без применения, правят и только потом применяют:

```bash
cd apps/backend
pnpm prisma migrate dev --name rename_bio --create-only   # создать, не применяя
# правка prisma/migrations/<дата>_rename_bio/migration.sql
pnpm prisma migrate dev                                   # применить
```

Закоммиченную миграцию не меняют: у других она уже может быть применена, и Prisma заметит правку по контрольной сумме. Исправление — новой миграцией. Если миграция ещё только у вас, её можно удалить и создать заново.

### Переименование поля или модели

Prisma Migrate не записывает, что именно вы сделали со схемой: она сравнивает два снимка, «было» и «стало». В снимках видно только, что поле `bio` исчезло, а поле `biography` появилось, — отличить по ним переименование от удаления одного поля и добавления другого нельзя. Поэтому Prisma генерирует второе:

```sql
ALTER TABLE "Profile" DROP COLUMN "bio",
ADD COLUMN "biography" TEXT NOT NULL;
```

Данные колонки при этом теряются. Замените SQL на переименование:

```sql
ALTER TABLE "Profile" RENAME COLUMN "bio" TO "biography";
```

Так же с моделью: `ALTER TABLE ... RENAME TO ...` вместо удаления и создания таблицы.

### Обязательное поле в таблице с данными

Колонку `NOT NULL` без значения по умолчанию нельзя добавить в таблицу, где уже есть строки, — миграция упадёт. Варианты:

- задать значение по умолчанию в схеме (`@default(...)`);
- разбить миграцию на три шага в одном `migration.sql`: добавить колонку без `NOT NULL`, заполнить её `UPDATE`, затем `ALTER COLUMN ... SET NOT NULL`.

### Без простоя: expand and contract

Если старая версия приложения какое-то время работает с уже обновлённой БД — несколько экземпляров, постепенная выкатка, — переименование даже через `RENAME` её сломает. Тогда изменение разбивают на шаги, каждый из которых совместим с текущим кодом:

1. **Expand**: добавить новое поле, приложение пишет в оба, читает из старого.
2. Отдельной миграцией скопировать данные: `UPDATE "Profile" SET biography = bio;`.
3. Приложение читает из нового поля, затем перестаёт писать в старое.
4. **Contract**: удалить старое поле.

Подробнее — в [документации Prisma](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/customizing-migrations#example-use-the-expand-and-contract-pattern-to-evolve-the-schema-without-downtime).

## Когда что-то пошло не так

### Миграция упала

`predev` остановится на шаге `migrations`, а Prisma сообщит причину:

```
Error: P3018
A migration failed to apply. New migrations cannot be applied before the error is recovered from.
Migration name: 20261002000000_add_task_priority
Database error:
ERROR: column "priority" of relation "Task" contains null values
```

Упавшая миграция записывается в `_prisma_migrations`, и следующие запуски `deploy` отказываются работать, пока её не разберут:

```
Error: P3009
migrate found failed migrations in the target database, new migrations will not be applied.
```

**Локально, если данные не нужны**: исправьте причину — например, SQL в своей ещё не закоммиченной миграции — и [пересоздайте БД](#сбросить-локальную-бд).

**Если данные нужно сохранить**: посмотрите состояние и отметьте миграцию вручную:

```bash
cd apps/backend
pnpm prisma migrate status                                    # что применено, что упало
pnpm prisma migrate resolve --rolled-back "<имя миграции>"    # откатили изменения вручную — применить заново
pnpm prisma migrate resolve --applied "<имя миграции>"        # довели изменения вручную — считать применённой
```

Если миграция успела выполниться частично, перед `--rolled-back` откатите уже сделанные шаги вручную. Подробнее — в [документации Prisma](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/patching-and-hotfixing#failed-migration).

### `migrate dev` предлагает сбросить БД

`migrate dev` перед созданием миграции сверяет историю с БД и останавливается, если они разошлись:

```
Drift detected: Your database schema is not in sync with your migration history.
```

Частые причины:

- **Переключение веток.** В другой ветке была миграция, она применена к локальной БД, а в текущей ветке её файла нет.
- **Изменена уже применённая миграция.** Prisma хранит контрольную сумму каждой миграции и замечает правку.
- **БД изменили в обход миграций** — вручную или через `prisma db push`.

Правильное решение — устранить причину: вернуть недостающий файл (переключиться обратно на ветку с ним) или откатить правку применённой миграции. Если локальные данные не нужны, проще согласиться на сброс.

`migrate deploy`, который запускает `pnpm dev`, такие расхождения не ищет: об изменённой миграции он только предупреждает, а недостающую и ручные правки БД не замечает. Проверить историю вручную — `pnpm prisma migrate status` из `apps/backend`: он покажет неприменённые, упавшие и отсутствующие локально миграции.

### Сбросить локальную БД

Пересоздать БД и применить все миграции заново — **все данные будут удалены**:

```bash
cd apps/backend
pnpm prisma migrate reset   # спросит подтверждение
pnpm prisma db seed         # seed после сброса запускается отдельно
```

Seed создаёт admin-аккаунт — [подробнее](/guide/database#seed-admin-аккаунт).
