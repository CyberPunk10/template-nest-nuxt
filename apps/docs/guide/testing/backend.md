# Тесты backend

Тестовый стек — [Jest](https://jestjs.io/) как раннер, [ts-jest](https://kulshekhar.github.io/ts-jest/) для трансформации TypeScript, `@nestjs/testing` для сборки модулей и [Supertest](https://github.com/ladjs/supertest) для HTTP-запросов. Всё это ставится вместе с `nest new`, отдельной настройки не требует.

## Запуск

Команды ниже записаны в короткой форме — так они выглядят из `apps/backend`. Из корня монорепо к любой добавляется `--filter @repo/backend`; про него и про запуск по всем пакетам сразу — в [общем разделе](./).

Кроме `test` и `test:e2e`, у backend есть команды для повседневной работы:

| Команда           | Что делает                                                     |
| ----------------- | -------------------------------------------------------------- |
| `pnpm test:watch` | Перезапускает затронутые тесты при сохранении файла            |
| `pnpm test:cov`   | Считает покрытие, HTML-отчёт кладёт в `apps/backend/coverage/` |
| `pnpm test:debug` | Запускает Jest под инспектором Node для отладки в IDE          |

Запустить один файл или один тест:

```bash
pnpm test tasks.service                    # файлы, чей путь содержит строку
pnpm test -t 'не затирает поля'            # тесты, чьё имя содержит строку
pnpm test:e2e --testPathPatterns=tasks     # то же для e2e

# то же из корня монорепо
pnpm --filter @repo/backend test tasks.service
```

Флаги пишутся без разделителя `--`: pnpm и так передаёт неизвестные ему аргументы в скрипт, а явный `--` он передаст дальше буквально, и Jest примет его за путь к файлу.

## Три набора тестов

Наборы разведены по расположению и по конфигурации.

|               | Юнит-тесты                     | E2E-тесты                        | E2E rate limiting                |
| ------------- | ------------------------------ | -------------------------------- | -------------------------------- |
| Команда       | `pnpm test`                    | `pnpm test:e2e`                  | `pnpm test:e2e:throttle`         |
| Где лежат     | `src/**/*.spec.ts`             | `test/default/*.e2e-spec.ts`     | `test/throttle/*.e2e-spec.ts`    |
| Конфигурация  | секция `jest` в `package.json` | `test/jest-e2e.json`             | `test/jest-e2e-throttle.json`    |
| Что поднимают | один класс с заглушками        | всё приложение через `AppModule` | приложение с включённым троттлером |
| Транспорт     | вызов метода напрямую          | HTTP через Supertest             | HTTP через Supertest             |

Раскладка файлов — общая для репозитория ([Соглашения](./#соглашения)): `tasks.service.ts` → `tasks.service.spec.ts` рядом, e2e — в `test/`.

Специфика Jest здесь в том, что наборам нужны **отдельные конфиги**, а не один с несколькими проектами: у них разный `rootDir` — юнит-набор смотрит в `src`, e2e в корень пакета, чтобы видеть и `test/`, и `src/`. Отсюда и разные правила отбора файлов (`testRegex` у юнит-набора, `testMatch` у e2e): иначе каждый набор подхватывал бы файлы другого.

Тесты rate limiting вынесены в третий набор из-за окружения. В обычных тестах троттлер отключён (`APP_ENV=test`), иначе накопленные счётчики ломали бы соседние проверки. Но тесту на `429` он как раз нужен, поэтому его `setupFiles` поднимает `APP_ENV=production` и опускает `THROTTLE_LIMIT` до `12` — лимит достижим за секунды. Совместить это с остальными e2e в одном конфиге нельзя: настройки задаются до загрузки модулей и действуют на весь прогон.

## Юнит-тесты

Тестируемый класс собирается через `Test.createTestingModule` — тот же DI-контейнер, что и в бою, только с подменёнными зависимостями:

```ts
const module: TestingModule = await Test.createTestingModule({
  providers: [TasksService],
}).compile()

service = module.get<TasksService>(TasksService)
```

Модуль пересоздаётся в `beforeEach`, а не в `beforeAll`. `TasksService` хранит задачи в памяти самого экземпляра, и общий сервис на весь файл означал бы, что задачи из одного теста видны в следующем: тесты начнут зависеть от порядка запуска и падать по одному при перестановке.

Зависимость, которая не участвует в проверяемом поведении, подменяется заглушкой. `AppController` читает конфиг, но поднимать ради этого `ConfigModule` и разбирать `.env` незачем:

```ts
{
  provide: ConfigService,
  useValue: { get: (key: string, defaultValue?: unknown) => env[key] ?? defaultValue },
}
```

Заглушка повторяет сигнатуру настоящего метода целиком, включая второй аргумент — значение по умолчанию. Упрощённая заглушка `(key) => env[key]` вела бы себя иначе, чем боевой `ConfigService`, и тест начал бы врать в тот момент, когда код воспользуется дефолтом.

### Проверяйте тот объект, который придёт в бою

Разница между литералом и экземпляром DTO — не формальность. `ValidationPipe` с `transform: true` отдаёт в сервис не тот объект, что пришёл в теле запроса, а экземпляр класса DTO, где **все** объявленные поля присутствуют, и непереданные равны `undefined`:

```ts
plainToInstance(UpdateTaskDto, { description: 'Новое' })
// UpdateTaskDto { title: undefined, description: 'Новое' }
// Object.keys(dto) → ['title', 'description']
```

Тест, передающий в `service.update()` литерал `{ description: 'Новое' }`, проверяет путь, которого в приложении нет. Поэтому в `tasks.service.spec.ts` DTO для таких проверок строится ровно так же, как это делает пайп — через `plainToInstance`.

## E2E-тесты

Приложение собирается из настоящего `AppModule` и отвечает на реальные HTTP-запросы:

```ts
const moduleFixture = await Test.createTestingModule({ imports: [AppModule] }).compile()
app = setupApp(moduleFixture.createNestApplication())
await app.init()
```

`app.init()` поднимает приложение, но не занимает порт — Supertest работает с HTTP-сервером напрямую через `app.getHttpServer()`. Порт `PORT` при этом свободен, тесты можно запускать параллельно с `pnpm dev`.

Приложение обязательно закрывается в `afterAll`/`afterEach`: без `app.close()` Jest не завершится и напечатает предупреждение об открытых хендлах.

### Конфигурация приложения не дублируется в тестах

Глобальные middleware, пайпы и фильтры перечислены один раз — в `src/setup-app.ts`, который вызывают и `main.ts`, и все e2e-тесты:

```ts
export function setupApp(app: INestApplication): INestApplication {
  app.use(cookieParser())
  app.useGlobalFilters(new HttpExceptionFilter())
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }))
  return app
}
```

`JwtStrategy` читает токен из `req.cookies` — без `cookieParser` любой защищённый роут отдаёт `401`, даже когда куки в запросе есть.

`Test.createTestingModule` собирает только модули — всё, что в бою навешивается в `main.ts`, в тестовом приложении отсутствует. Если продублировать этот список в тесте копипастой, e2e будет проверять приложение с другой конфигурацией, чем production, и разойдётся с ним при первой же правке: снимите `forbidNonWhitelisted` в `main.ts` — тесты останутся зелёными, потому что в своей копии настройка на месте. Общая функция делает такой разъезд невозможным.

CORS, Swagger и `listen` в `setupApp` не входят: к проверяемому поведению эндпоинтов отношения не имеют. CORS срабатывает по заголовку `Origin`, которого supertest не шлёт, Swagger монтирует отдельный роут, а `listen` открывает порт — в тестах приложение живёт в памяти.

### Состояние между тестами

`auth.e2e-spec.ts` поднимает приложение один раз в `beforeAll`, а изоляция обеспечивается данными: `beforeEach` вызывает `cleanupTestData()` и удаляет тестовых пользователей. Это заметно дешевле, чем пересоздавать приложение на каждый тест.

В `app.e2e-spec.ts` состояния нет вовсе — там достаточно одного `beforeAll`.

### Переменные окружения

`AppModule` вызывает `ConfigModule.forRoot()` прямо в декораторе `@Module`, то есть окружение валидируется **в момент импорта модуля**. Задать переменную внутри `beforeAll` уже поздно — импорт к этому времени выполнен.

Поэтому e2e-конфиг подключает `test/setup-env.ts` через `setupFiles`: этот хук выполняется до загрузки тестовых файлов.

```ts
process.env.CORS_ORIGIN ??= 'http://localhost:3200'
```

`CORS_ORIGIN` — единственная переменная без значения по умолчанию в [Joi-схеме](../env-variables), без неё приложение не стартует. Оператор `??=` не перетирает уже заданное значение: локально подхватится `.env`, в CI сработает подстановка. Схема принимает `NODE_ENV=test` — Jest выставляет его сам.

## Что покрыто тестами

`pnpm test:cov` печатает таблицу покрытия. Из отчёта исключены сами спеки, `main.ts` (bootstrap проверяется целиком через e2e) и `src/generated/` — код, сгенерированный Prisma в ветках с базой данных: он занижал бы общую цифру, не имея отношения к коду проекта. О том, почему процент покрытия сам по себе мало значит, — в [общем разделе](./#полезно-помнить).

Сейчас в шаблоне:

- **`tasks.service.spec.ts`** — CRUD в памяти: генерация `id` и меток времени, фильтрация по владельцу, частичное обновление без затирания полей, `NotFoundException` на неизвестный `id` и `ForbiddenException` на чужую задачу
- **`users.service.spec.ts`** — CRUD пользователей: `NotFoundException` на неизвестный `id`, `ConflictException` при дублирующемся email — и при создании, и при обновлении
- **`app.controller.spec.ts`** — `/health` и `/dev/config`, включая разное поведение `publicUrl` в dev и production
- **`http-exception.filter.spec.ts`** — приведение ошибок к единому JSON и то, что текст неожиданного исключения не утекает клиенту
- **`auth.e2e-spec.ts`** — полный цикл: регистрация, вход, refresh с ротацией токена, logout, reuse detection, доступ к защищённым роутам
- **`app.e2e-spec.ts`** — `/`, `/health`, `/dev/config` и `404` на неизвестный маршрут
- **`throttle.e2e-spec.ts`** — `429` после превышения лимита запросов (отдельный набор, см. выше)

## Добавление тестов

Для нового модуля:

1. Юнит-тест на сервис — `src/modules/<имя>/<имя>.service.spec.ts`. Проверяйте бизнес-логику: что возвращается, какие исключения бросаются, что меняется в состоянии
2. E2E-тест на контроллер — `test/default/<имя>.e2e-spec.ts`. Проверяйте контракт HTTP: коды ответов, форму тела, валидацию. Приложение поднимайте через `setupApp` — иначе валидация и фильтр ошибок работать не будут, и тест зафиксирует не те коды, что отдаст живой сервер

Отдельный юнит-тест на контроллер обычно избыточен: если контроллер только делегирует вызов сервису, проверять в изоляции нечего — весь его смысл (маршруты, пайпы, коды статусов) виден только на уровне e2e.
