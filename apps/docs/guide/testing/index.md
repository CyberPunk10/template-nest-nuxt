# Тестирование

Тесты живут внутри того приложения, которое проверяют: у каждого пакета workspace свой раннер, своя конфигурация и свои зависимости. Общего тестового пакета в монорепо нет — приложения на NestJS и Nuxt проверяются по-разному, и общий конфиг пришлось бы разветвлять на каждое различие.

Из корня монорепо запуск при этом один:

```bash
pnpm test         # юнит-тесты во всех пакетах
pnpm test:e2e     # e2e-тесты во всех пакетах
```

Обе команды выполняют `pnpm -r`, то есть проходят по всем пакетам workspace и вызывают одноимённый скрипт. Пакет, у которого такого скрипта нет, пропускается молча — добавить тесты новому приложению значит добавить ему скрипт `test` в `package.json`, ничего не меняя в корне.

Запуск можно сузить до одного пакета, не переходя в его папку — через `--filter`:

```bash
pnpm --filter @repo/backend test           # только юнит-тесты backend
pnpm --filter @repo/backend test:e2e       # только e2e-тесты backend
pnpm --filter @repo/backend test:watch     # любой скрипт этого пакета
```

`--filter` принимает имя пакета из его `package.json`; полное имя можно сократить (`backend`) или заменить путём (`./apps/backend`). Аргументы после имени скрипта уходят в него без изменений, поэтому флаги раннера работают и отсюда.

Одна особенность стоит внимания: если у выбранного пакета запрошенного скрипта нет, pnpm завершается **с кодом 0 и пустым выводом**. Ошибки не будет — в CI такой прогон легко принять за успешный, хотя не запустилось ничего.

## Два уровня

Разделение на юнит- и e2e-тесты сквозное для всего репозитория, независимо от раннера.

**Юнит-тесты** проверяют одну единицу кода в изоляции: зависимости подменяются заглушками, ничего постороннего не поднимается. Быстрые — счёт идёт на миллисекунды, поэтому их удобно держать в watch-режиме во время работы.

**E2E-тесты** проверяют собранное приложение целиком, обращаясь к нему снаружи — так же, как это делает настоящий клиент.

Разделение не формальное: у уровней разная область отказа. Юнит-тесты отвечают на вопрос «правильно ли работает эта функция», e2e — «правильно ли собрано приложение». Ошибка в проводке между слоями — не подключённая глобальная настройка, разошедшийся контракт между модулями — на первом уровне не видна в принципе: каждая часть по отдельности исправна.

Поэтому e2e не заменяют юнит-тесты и не заменяются ими. Юнит-тестами покрывается логика с ветвлениями, e2e — контракт приложения наружу; дублировать все ветки на медленном уровне смысла нет.

## Соглашения

Общие для всех приложений шаблона:

- **Юнит-тесты лежат рядом с проверяемым файлом**, отличаясь суффиксом: `foo.ts` → `foo.spec.ts`. Так тест не теряется при переносе модуля и сразу виден в дереве проекта
- **E2E-тесты вынесены в отдельную папку** приложения: они относятся не к конкретному файлу, а к приложению целиком
- **Каждый тест начинает с чистого состояния.** Тесты, зависящие от порядка запуска, начинают падать по одному при перестановке или параллельном прогоне — а раннеры переупорядочивают файлы свободно
- **Тест проверяет тот же объект, что придёт в бою.** Упрощённая заглушка или литерал вместо настоящей структуры данных даёт зелёный тест на пути, которого в приложении нет

## Полезно помнить

Покрытие — ориентир, а не цель. Строка, которую тест выполнил, но результат не проверил, засчитывается как покрытая, поэтому высокий процент сам по себе ничего не гарантирует.

Надёжнее проверять тесты мутацией: внесите ошибку в код и убедитесь, что тест покраснел. Тест, остающийся зелёным на сломанном коде, не проверяет ничего — и хуже отсутствующего, потому что создаёт ложное ощущение защиты.
