# Релизы

Проект состоит из двух репозиториев, и у каждого свой релиз. Они связаны: генератор всегда скачивает конкретный релиз шаблона, поэтому выпускать их нужно в определённом порядке.

## Два репозитория

|  | Шаблон | Генератор |
| --- | --- | --- |
| Репозиторий | [`CyberPunk10/template-nest-nuxt`](https://github.com/CyberPunk10/template-nest-nuxt) | [`CyberPunk10/create-nest-nuxt`](https://github.com/CyberPunk10/create-nest-nuxt) |
| Что это | Сам код будущего проекта: три варианта в трёх ветках (`main` → `auth-session` → `postgres-prisma`) | npm-пакет с CLI: спрашивает вариант и язык, скачивает шаблон, подчищает его под проект пользователя |
| Как им пользуются | Не напрямую — через генератор | `npx create-nest-nuxt my-app` |
| Что такое релиз | Три git-тега, по одному на ветку, и один GitHub Release | Git-тег, GitHub Release и публикация в npm |
| Формат тега | `main@0.1.1`, `auth-session@0.1.1`, `postgres-prisma@0.1.1` | `v0.2.0` |
| Кто выпускает | Вы, руками | release-please в GitHub Actions — вам остаётся смержить Release PR и подтвердить публикацию в npm |
| CHANGELOG | Нет — описание пишется в GitHub Release | `CHANGELOG.md`, ведёт release-please |

Версии у репозиториев независимые: генератор 0.2.0 может работать с шаблоном 0.1.1. Поле `version` в `package.json` шаблона (`0.0.1`) в релизах не участвует — версия шаблона живёт только в тегах.

## Как они связаны

В генераторе есть константа `TEMPLATE_VERSION` в `src/variants.ts` — релиз шаблона, с которым проверена эта версия генератора. По ней генератор скачивает тег `<вариант>@<TEMPLATE_VERSION>`:

```ts
export const TEMPLATE_VERSION = '0.1.1'
// вариант auth-session → gh:CyberPunk10/template-nest-nuxt#auth-session@0.1.1
```

Поэтому одна и та же версия генератора всегда даёт один и тот же проект: `npx create-nest-nuxt@0.2.0` через год скачает тот же шаблон, что и сегодня. Свежие коммиты в ветках шаблона до пользователей не доходят, пока не выпущены релизом и генератор не переведён на него.

Отсюда главное правило: **шаблон выпускается первым, генератор — за ним.** Генератор не может ссылаться на тег, которого ещё нет: скачивание упадёт.

```
ШАБЛОН                                ГЕНЕРАТОР
1. правки в ветках, CI зелёный
                                      2. проверка на головах веток шаблона
3. теги *@0.1.1 + GitHub Release
                                      4. TEMPLATE_VERSION = '0.1.1', CI зелёный
                                      5. мерж Release PR → npm → подтверждение
```

## Версии

Оба репозитория нумеруются по semver: `мажор.минор.патч`. Пока проект в бете, мажор — `0`.

- **Шаблон.** Номер выбираете вы. Одна версия на все три ветки, даже если изменилась только одна: так `TEMPLATE_VERSION` остаётся одной константой. Исправления — патч (`0.1.0` → `0.1.1`), заметные новые возможности — минор (`0.1.1` → `0.2.0`).
- **Генератор.** Номер выбирает release-please по типам коммитов с прошлого релиза: `fix:` — патч, `feat:` — минор. Изменение с `!` или `BREAKING CHANGE` до версии 1.0 тоже поднимает только минор — так настроено в `release-please-config.json` (`bump-minor-pre-major`). Коммиты `chore:`, `docs:`, `ci:`, `build:`, `test:` версию не поднимают.

## Релиз шаблона

### 1. Убедиться, что ветки готовы

Все три ветки должны совпадать с `origin`, изменения из `main` — дойти по цепочке, CI — быть зелёным:

```bash
git fetch
git status -sb                                        # нет незапушенного
git log --oneline origin/auth-session..origin/main    # пусто — main влит в auth-session
git log --oneline origin/postgres-prisma..origin/auth-session   # пусто
gh run list -L 6                                      # последние прогоны CI — success
```

Если коммиты из `main` ещё не дошли до других веток, дождитесь branch-sync или сведите конфликт руками.

### 2. Проверить генератор на невыпущенном шаблоне

До тегов стоит убедиться, что генератор справляется с текущим состоянием веток: например, не переименован ли файл, который генератор удаляет. Команду запускайте в корне клона генератора:

```bash
cd ~/Projects/nest-nuxt/create-nest-nuxt
CNN_TEMPLATE_VERSION=branch pnpm test
```

Ваших файлов тесты не трогают. Перед запуском они сами собирают CLI в `dist/`, а проекты создают во временной папке системы (`/tmp/cnn-e2e-…`) и удаляют её в конце. Нужна сеть: шаблон скачивается с GitHub, а не берётся из ваших локальных клонов, поэтому незапушенные правки шаблона в проверку не попадут.

Это одна команда: `pnpm test` запускает тесты генератора, а `CNN_TEMPLATE_VERSION=branch` перед ней задаёт переменную окружения только на время этого запуска — в `.env` и в терминале она не остаётся. Среди тестов есть e2e: они запускают собранный CLI, и тот по-настоящему скачивает шаблон с GitHub. Без переменной он берёт теги `TEMPLATE_VERSION`, с `branch` — текущее состояние веток `main`, `auth-session` и `postgres-prisma`.

Упало — чините шаблон или генератор обычным коммитом и повторяйте.

### 3. Поставить теги

Теги ставятся на головы веток в `origin`:

```bash
git tag main@0.1.1 origin/main
git tag auth-session@0.1.1 origin/auth-session
git tag postgres-prisma@0.1.1 origin/postgres-prisma
git push origin main@0.1.1 auth-session@0.1.1 postgres-prisma@0.1.1
```

Тег — неизменяемый снимок. Если тег уже запушен и оказался ошибочным, не перемещайте его: кто-то мог успеть скачать шаблон по нему. Выпустите следующую патч-версию.

### 4. Создать GitHub Release

Один релиз на версию, на теге `main@…`. Тег только прикрепляет страницу релиза к коммиту, а описание может рассказывать о любой ветке. Пишется руками, по разделам:

1. **Все варианты** (`main`, `auth-session`, `postgres-prisma`) — изменения из `main`, они дошли до всех веток;
2. **Auth** (`auth-session`, `postgres-prisma`) — то, что сделано в `auth-session`;
3. **PostgreSQL** (`postgres-prisma`) — то, что сделано только в `postgres-prisma`.

Раздел без изменений пропустите. Дальше — как установить и требования к окружению. За образец берите [релиз 0.1.1](https://github.com/CyberPunk10/template-nest-nuxt/releases/tag/main@0.1.1).

Описание удобнее написать заранее во временном файле — например, `notes.md` вне репозитория, — и передать его команде:

```bash
gh release create main@0.1.1 --title 0.1.1 --notes-file notes.md --latest
```

То же можно сделать в браузере: **Releases → Draft a new release**, выбрать тег и вставить текст. Автоматическое описание (`--generate-notes`) не подходит — получается сплошной список коммитов без разделов по вариантам.

Описание и заголовок можно поправить и после публикации: кнопка **Edit** на странице релиза или `gh release edit main@0.1.1 --notes-file notes.md`. Тег при этом не меняется.

Списки изменений для каждого раздела:

```bash
git log --no-merges --oneline main@0.1.0..main@0.1.1                              # все варианты
git log --no-merges --oneline auth-session@0.1.0..auth-session@0.1.1 ^main@0.1.1  # только auth-session
git log --no-merges --oneline postgres-prisma@0.1.0..postgres-prisma@0.1.1 ^auth-session@0.1.1  # только postgres-prisma
```

В описании укажите требования к окружению — версии Node и pnpm — и команду установки с конкретной версией генератора, которая ставит этот шаблон: `npx create-nest-nuxt@0.2.0 my-app`, а не `@latest`. Через полгода `@latest` поставит уже другой шаблон, и описание старого релиза станет неверным. Версию генератора видно в его открытом Release PR — до публикации генератора команда работать не будет.

## Релиз генератора

### 1. Перевести генератор на новый шаблон

В `src/variants.ts` поменяйте `TEMPLATE_VERSION` на новую версию шаблона, закоммитьте и запушьте в `main`. Тип коммита решает, какую версию генератора предложит release-please:

- `fix: use template 0.1.1` — в шаблоне только исправления, будет патч;
- `feat: use template 0.2.0` — в шаблоне новые возможности, будет минор.

Если e2e-проверки ждали нового шаблона, коммитьте их вместе с `TEMPLATE_VERSION`: на старых тегах они бы упали.

### 2. Дождаться CI

CI генератора гоняет e2e уже на новых тегах, то есть проверяет ровно то, что получат пользователи. Красный CI — ничего не выпускайте, разберитесь.

### 3. Смержить Release PR

release-please держит открытым PR `chore(main): release X.Y.Z` и обновляет его после каждого push в `main`: следующая версия, `CHANGELOG.md`, `package.json`. Перед мержем прочитайте его описание — это и есть будущий CHANGELOG.

После мержа workflow `release.yml` сам:

1. ставит тег `vX.Y.Z` и создаёт GitHub Release;
2. ещё раз прогоняет typecheck и тесты;
3. отправляет пакет в npm на подтверждение (`npm stage publish`). Токен npm не нужен: npm доверяет именно этому workflow (trusted publishing), это указано в настройках пакета на npmjs.com.

### 4. Подтвердить публикацию

Пользователи пока не видят новую версию: workflow её только загрузил, а опубликовать может лишь мейнтейнер с двухфакторной аутентификацией. Так украденный токен GitHub не позволит выпустить версию от вашего имени.

```bash
npm stage list create-nest-nuxt    # загруженные версии и их id
npm stage approve <id>             # опубликовать — npm спросит код 2FA
```

Id есть и в логе workflow, в последней строке шага publish: `staged with id …`. То же можно сделать на странице пакета на npmjs.com. Если версия не нужна — `npm stage reject <id>`.

Команды работают из любой папки: они обращаются к реестру npm по id, а не к файлам проекта. Нужны две вещи:

- **npm 11.16 и новее** — в нём появился `npm stage`. Проверка: `npm -v`. Старее — переключите Node на актуальный: `nvm use 24.22.1`.
- **Вход в npm.** Проверка: `npm whoami` должен показать ваш логин. Если вместо него ошибка `ENEEDAUTH` или `401` — войдите:

  ```bash
  npm login
  ```

  npm откроет браузер, вы входите на npmjs.com с 2FA, и токен сохраняется в `~/.npmrc` — один на всю машину, не на проект. Выйти — `npm logout`.

### 5. Проверить публикацию

```bash
npm view create-nest-nuxt version          # новая версия
npx create-nest-nuxt@latest my-app         # проект создаётся и запускается
```

### Если публикация упала

Тег и GitHub Release к этому моменту уже созданы, и повторно release-please их не сделает. Запустите публикацию вручную на нужном теге:

```bash
gh workflow run release.yml -R CyberPunk10/create-nest-nuxt -f tag=v0.2.0
```

Workflow соберёт и проверит код этого тега и снова отправит его в npm на подтверждение.

## Если меняется только генератор

Шаги шаблона не нужны, `TEMPLATE_VERSION` остаётся прежним. Коммиты в `main` генератора → зелёный CI → мерж Release PR → подтверждение в npm.

## Что пока делается руками

- Теги шаблона и описание GitHub Release — нет скрипта, который проверил бы ветки и CI и поставил теги.
- У шаблона нет `CHANGELOG.md` — история изменений только в описаниях GitHub Release.
- Перевод генератора на новый шаблон — PR с новым `TEMPLATE_VERSION` не открывается сам после релиза шаблона.
- Пользователь не может выбрать другой релиз шаблона: флага вроде `--template <версия>` у генератора нет, он всегда берёт `TEMPLATE_VERSION`.
