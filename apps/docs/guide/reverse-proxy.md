# Reverse proxy

В Docker-режиме наружу смотрит один сервис — nginx из `infra/nginx/`. Он принимает весь внешний трафик и раскладывает его по приложениям во внутренней сети.

```
браузер  →  nginx:80
  │
  ├── /dev/docs/  →  /srv/docs       статика VitePress (отдаёт nginx с диска)
  ├── /api/docs   →  backend:3100    Swagger UI
  └── /*          →  frontend:3200   Nuxt SSR
                          │
                          └── backend:3100   API через BFF-прокси
```

Сам nginx обслуживает только два маршрута: документацию отдаёт с диска, Swagger проксирует в бэкенд. Всё остальное, включая запросы к API (`/api/backend/*`), уходит в Nuxt — для nginx они неотличимы от обычных запросов к фронтенду. В бэкенд их форвардит уже сам Nuxt.

## Почему порты приложений закрыты

`backend` и `frontend` объявляют порт через `expose`, а не `ports` — он виден внутри сети Docker, но на хост-машину не проброшен. Единственный публикуемый порт — у прокси.

```yaml
backend:
  expose:
    - '${BACKEND_INTERNAL_PORT}'
```

Приложение за прокси не должно быть доступно в обход него: иначе теряют смысл заголовки безопасности, лимиты и маршрутизация, которые прокси настраивает. Чем меньше открытых портов, тем меньше поверхность атаки — это обычная практика для production.

Если нужно обратиться к сервису напрямую, например чтобы понять, проблема в прокси или в самом приложении:

```bash
docker compose exec backend wget -qO- http://localhost:3100/health
```

## Почему `infra/`, а не `apps/`

Конвенция монорепо отводит `apps/` под приложения, `packages/` — под переиспользуемые библиотеки. Прокси не то и не другое: у него нет `package.json`, он не участвует в `pnpm install`, его не собирает workspace. Это инфраструктурный конфиг, поэтому он живёт в `infra/` — папке, куда со временем логично класть и остальную обвязку (мониторинг, скрипты деплоя).

## Что делает конфиг

`infra/nginx/nginx.conf.tpl` отвечает не только за маршрутизацию.

**Документация как статика.** `/dev/docs/` nginx отдаёт с диска через `alias` — проксировать некуда, за этим путём нет работающего процесса:

```nginx
location /dev/docs/ {
    alias /srv/docs/;
    try_files $uri $uri.html $uri/index.html =404;
    error_page 404 /dev/docs/404.html;
}
```

`alias`, а не `root`: путь на диске (`/srv/docs/`) не повторяет URL (`/dev/docs/`), и `alias` подменяет совпавший префикс, тогда как `root` дописал бы его к пути.

`$uri.html` нужен потому, что VitePress собирает страницы файлами вида `guide/x.html`, а ссылается на них без расширения. Финальный `=404` обязателен: без него несуществующая страница отдавалась бы с кодом **200** — тело правильное, статус нет.

**Кеширование ассетов.** Файлы в `/dev/docs/assets/` собраны с хешем в имени: содержимое по такому URL не меняется никогда, поэтому браузеру разрешено не перепроверять его:

```nginx
location /dev/docs/assets/ {
    alias /srv/docs/assets/;
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

**Заголовки безопасности** — `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, плюс `server_tokens off`, чтобы версия nginx не светилась в ответах и на страницах ошибок.

::: warning add_header не наследуется
Если вложенный `location` объявляет **свой** `add_header`, родительские заголовки в нём перестают действовать — целиком, а не по одному. Поэтому в `/dev/docs/assets/`, где задан `Cache-Control`, заголовки безопасности продублированы явно. Это частый источник дыр: заголовки «есть в конфиге», но не приходят на часть маршрутов.
:::

**WebSocket.** Заголовки `Upgrade`/`Connection` проброшены в Nuxt, чтобы работал HMR, если фронтенд когда-нибудь окажется за прокси в dev-режиме:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

`map` нужен потому, что константу `Connection: upgrade` прописать нельзя — на обычных HTTP-запросах это сломало бы keep-alive. Здесь значение подставляется только когда клиент прислал заголовок `Upgrade`.

**Swagger.** `proxy_pass` для `/api/docs` идёт **без** завершающего слэша — так URI сохраняется целиком. Swagger UI грузит свои ассеты по абсолютным путям от `/api/docs/`, и переписывание префикса их бы сломало.

**gzip** включён для текстовых типов: HTML, CSS, JS, JSON, SVG.

## Чего в конфиге намеренно нет

**HSTS** — заголовок надолго заставляет браузер ходить только по https. На http-сайте это закроет к нему доступ, поэтому строка оставлена закомментированной: раскомментировать вместе с TLS.

**Content-Security-Policy** — рабочий набор директив зависит от того, какие внешние ресурсы использует приложение. Неверная политика молча ломает страницы, поэтому политика не задана: настраивать под конкретный проект.

**TLS** — сертификатов нет, прокси слушает обычный HTTP. В большинстве сценариев деплоя (managed-платформы, облачные балансировщики, Ingress в Kubernetes) TLS терминируется снаружи, и до прокси доходит уже расшифрованный трафик. Если разворачиваете на своём VPS — понадобится certbot либо переход на Caddy с автоматическим HTTPS.

## Шаблон и envsubst

Файл `nginx.conf.tpl` — не готовый конфиг. Встроенный entrypoint образа `nginx:alpine` прогоняет `*.template` из `/etc/nginx/templates/` через `envsubst` и кладёт результат в `/etc/nginx/conf.d/` до старта nginx.

Подводный камень: `envsubst` подставляет **все** `$переменные`, включая nginx-овские `$uri`, `$host`, `$http_upgrade`. Они не заданы в окружении, поэтому превратились бы в пустые строки и сломали конфиг. Спасает фильтр:

```dockerfile
ENV NGINX_ENVSUBST_FILTER='^(NGINX_INTERNAL_PORT|FRONTEND_INTERNAL_PORT|BACKEND_INTERNAL_PORT)$'
```

Добавляете в шаблон новую переменную — допишите её сюда, иначе она останется в конфиге как есть.

## Проверка

Посмотреть итоговый конфиг после подстановки:

```bash
docker compose exec nginx cat /etc/nginx/conf.d/default.conf
```

Проверить заголовки на конкретном маршруте:

```bash
curl -sI http://localhost/dev/docs/
```

Логи доступа и ошибок:

```bash
docker compose logs nginx
```

## В dev-режиме прокси нет

`pnpm dev` поднимает три процесса на своих портах, без nginx. Это осознанно: Vite-овский HMR держит WebSocket-соединение, и прокси перед ним требует дополнительной настройки (`server.hmr.clientPort`), которая усложняет самый частый сценарий работы ради симметрии с продом.

Практическое следствие — адреса в dev и в Docker различаются, поэтому они вынесены в переменные окружения:

| Что          | dev                               | Docker                       |
| ------------ | --------------------------------- | ---------------------------- |
| Приложение   | `http://localhost:3200`           | `http://localhost/`          |
| Документация | `http://localhost:5173/dev/docs/` | `http://localhost/dev/docs/` |
| Swagger      | `http://localhost:3100/api/docs`  | `http://localhost/api/docs`  |

Пути при этом совпадают — различается только хост с портом. `base` документации захардкожен как `/dev/docs/`, чтобы не расходились и они.
