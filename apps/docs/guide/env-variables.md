# ENV-переменные

## Файлы

Четыре независимых `.env` — по одному на приложение плюс корневой для Docker:

```
template-nest-nuxt/
├── .env[.example]            ← читает docker-compose.yml
├── apps/
│   ├── backend/
│   │   └── .env[.example]    ← читает NestJS напрямую
│   ├── frontend/
│   │   └── .env[.example]    ← читает Nuxt напрямую
│   └── docs/
│       └── .env[.example]    ← VitePress (dotenv в config.ts)
└── ...
```

Каждое приложение читает **только свой** `.env`, не зная о существовании остальных. Корневой `.env` нужен для docker-compose.

В репозитории лежат только `.env.example`. Рабочие `.env` нужно создать, для этого есть три способа:

- **автоматически** — при первом `pnpm dev` или `pnpm docker:up` их под капотом создают [`predev.mjs` / `predocker.mjs`](./structure/scripts/);
- **командой** — `pnpm env:copy` создаёт все четыре разом, ничего не запуская;
- **вручную** — скопировать `.env.example` → `.env` в корне и в каждой `apps/*/`.

Существующие файлы **не перезаписываются**: команда создаёт только те, которых нет.

Если нужно именно вернуть исходные значения:

```bash
pnpm env:copy:force
```

::: warning
`pnpm env:copy:force` перезаписывает `.env` файлы **целиком**, а не дописывает недостающие строки. Всё, что вы меняли руками, будет потеряно.
:::

## Порты

Проект запускается двумя способами, и порты в них означают разное.

**`pnpm dev`** — три процесса прямо на вашей машине, у каждого свой порт:

```
localhost:3100   backend
localhost:3200   frontend
localhost:5173   docs
```

Открываете нужный адрес в браузере напрямую. Порты задаются в `PORT` — по одному в `apps/*/.env`.

**Docker** — те же приложения в контейнерах, но наружу открыт **один** порт: reverse proxy на `80`. Он и раскладывает запросы по сервисам:

```
localhost/            → frontend
localhost/api/docs    → backend (Swagger)
localhost/dev/docs/   → статика документации
```

Внутри сети приложения по-прежнему слушают порты, но адресуются по имени сервиса — `http://backend:3100`. Снаружи эти порты недоступны. Задаются они в корневом `.env`, потому что нужны Docker Compose, а не самим приложениям.

### Сводка

| Переменная        | Файл            | Что задаёт                        |
| ----------------- | --------------- | --------------------------------- |
| `PORT`            | `apps/*/.env`   | Порт процесса при `pnpm dev`      |
| `*_INTERNAL_PORT` | `.env` (корень) | Порт процесса внутри контейнера   |
| `NGINX_HOST_PORT` | `.env` (корень) | Единственный порт приложения наружу в Docker |
| `POSTGRES_PORT`   | `.env` (корень) | Хост-порт БД — доступ с машины    |

У документации `apps/docs` `*_INTERNAL_PORT` нет, т.к. в Docker её статика лежит прямо в образе прокси, отдельного процесса не существует. VitePress поднимает свой сервер только при `pnpm dev` — отсюда `PORT=5173`.

### Почему значения нельзя объединить

Хотя числа совпадают (3100 и 3200 в обоих режимах), это разные вещи. В dev порт занят на вашей машине, и его может отобрать другое приложение. В контейнере порт живёт в изолированном сетевом пространстве: конфликтовать не с чем, а снаружи он всё равно не виден.

Практическое следствие: занят локальный 3200 — меняете `PORT` в `apps/frontend/.env`, и Docker это никак не затрагивает.

### Почему у backend и frontend нет хост-порта

В `docker-compose.yml` для них указан `expose`, а не `ports`: порт объявлен, но на хост не проброшен. Достучаться можно только через reverse proxy — [почему так](./reverse-proxy#почему-порты-приложении-закрыты).

### Почему `PORT` из `apps/*/.env` не действует в Docker

Файл в контейнер попадает — через `env_file` в compose. Но строка `environment: PORT` перекрывает его при старте: `environment` в Compose всегда сильнее `env_file`.

Так и задумано. Иначе локальный `PORT`, изменённый под свои нужды, уезжал бы в контейнер и ломал бы связку с nginx. [Подробный разбор](./structure/docker-compose#внутренние-порты).

## CORS_ORIGIN

Из всех переменных эта чаще других приводит к неочевидной поломке.

Браузер не даёт странице с одного адреса читать ответы с другого, если сервер явно не разрешил. Разрешение выдаётся заголовком `Access-Control-Allow-Origin`, и его значение бэкенд берёт из `CORS_ORIGIN`. Сравнение строгое, посимвольное.

Поломка тихая: сервер отвечает **200**, в логах порядок, но в браузере запрос помечен как неудавшийся и данные до приложения не доходят. Легко искать причину в коде, хотя дело в одной строке `.env`.

### С чем должно совпадать

| Режим      | Значение                | Совпадает с                       |
| ---------- | ----------------------- | --------------------------------- |
| `pnpm dev` | `http://localhost:3200` | `PORT` в `apps/frontend/.env`     |
| Docker     | `http://localhost`      | `PUBLIC_ORIGIN` в корневом `.env` |

Меняете порт фронтенда в dev — поправьте `CORS_ORIGIN` в `apps/backend/.env`. Меняете порт прокси или разворачиваете на сервере — поправьте `PUBLIC_ORIGIN` в корневом `.env` (на сервере это `https://<домен>`).

### Почему в Docker без порта

Браузер **опускает стандартный порт**: `:80` для http, `:443` для https. Открывая `http://localhost`, он пришлёт `Origin: http://localhost` — без порта. Записанное `http://localhost:80` не совпало бы, и все запросы к API заблокировались бы.

### В production порт не участвует

Когда фронтенд и бэкенд разъедутся по доменам:

```
frontend:  https://app.example.com    ← этот адрес пришлёт браузер
backend:   https://api.example.com
CORS_ORIGIN=https://app.example.com
```

Адреса различаются доменом, порт стандартный и в заголовке не появляется. `PORT` в `apps/frontend/.env` никуда не делся — Nuxt по-прежнему слушает 3200, просто за прокси.

То есть связь «`CORS_ORIGIN` ↔ порт фронтенда» существует, только пока оба на `localhost`.

### Как проверить

```bash
curl -sI -H "Origin: http://localhost:3200" http://localhost:3100/health | grep -i access-control
```

Нет `Access-Control-Allow-Origin` с вашим адресом — значение неверное.

## Связанные переменные

Часть переменных ссылается на порт соседнего приложения. Меняете порт — поправьте и то, что на него смотрит.

**Порт frontend** (`PORT` в `apps/frontend/.env`)

- `CORS_ORIGIN` в `apps/backend/.env` — иначе бэкенд отклонит запросы с другого origin
- `DASHBOARD_URL` в `apps/docs/.env` — иначе кнопка «Посмотреть демо» уведёт не туда

**Порт backend** (`PORT` в `apps/backend/.env`)

- `NUXT_BACKEND_URL` в `apps/frontend/.env` — иначе SSR не достучится до API

::: tip В Docker связок нет
Там адреса задаются через имена сервисов (`http://backend:3100`), а не порты на хосте. Сверять порты нужно только для `pnpm dev`.
:::

## Пустые значения

Переменные бэкенда с дефолтами (`NODE_ENV`, `APP_ENV`, `PORT`, `SWAGGER_ENABLED`) помечены в Joi-схеме как `.empty('')`. Запись `FOO=` — обычный способ «сбросить» переменную в compose или CI — трактуется как «не задано», и подставляется дефолт.

У обязательного `CORS_ORIGIN` такой пометки нет намеренно: пустой origin — ошибка конфигурации, приложение должно упасть на старте.
