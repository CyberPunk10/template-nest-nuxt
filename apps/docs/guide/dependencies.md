# Обновление зависимостей

Версии пакетов записаны в двух местах: диапазоны (`^11.2.8`) — в `package.json` каждого пакета workspace, точные установленные версии всего дерева — в `pnpm-lock.yaml`. Обновление — это осознанное изменение обоих файлов, которое видно в diff и проходит те же проверки, что и любой другой код.

## 1. Посмотреть, что устарело

```bash
pnpm outdated -r
```

Показывает по всем пакетам workspace установленную и последнюю опубликованную версию.

## 2. Обновить в пределах диапазонов

```bash
pnpm update -r    # то же самое — скрипт pnpm deps:sync
```

`-r` — по всем пакетам workspace. Команда поднимает пакеты до последних версий, которые допускают диапазоны, и записывает новые значения в `package.json`. Лок-файл дополняется, а не пересчитывается с нуля. Для `^` это минорные и патч-версии, для `~` — только патч-версии.

Обновить один пакет:

```bash
pnpm update -r vue
```

## 3. Мажорные версии — по одной

Мажорная версия выходит за диапазон и может ломать API, поэтому такие обновления делайте отдельно от остальных и по одному пакету:

```bash
pnpm update -r --latest --interactive
```

Команда покажет список доступных обновлений и даст выбрать нужные. Перед мажорным обновлением прочитайте release notes или migration guide пакета.

## 4. Проверить

Прогоните линтер, проверку типов, сборку и тесты:

```bash
pnpm lint
pnpm type-check
pnpm build
pnpm test
pnpm test:e2e
```

## Придержать версию

Если новая версия пакета сломана, замените `^` на `~` — тогда `pnpm update -r` будет брать только патч-версии и не подтянет сломанную минорную. В сообщении коммита укажите причину и условие, при котором можно вернуть `^`, например ссылку на issue.

## Обновить pnpm

```bash
pnpm self-update
```

В проекте команда меняет только версию в `packageManager` корневого `package.json`, глобальный pnpm не трогает. Закоммитьте `package.json` вместе с `pnpm-lock.yaml` — у остальных разработчиков pnpm переключится на новую версию сам при первом запуске.

## Уязвимости

```bash
pnpm audit
```

Часть уязвимостей сидит глубоко в транзитивных зависимостях инструментов сборки и не устраняется обновлением на вашей стороне. Смотрите на путь (`Paths`): уязвимость в пакете, который попадает в production-сборку, важнее, чем в dev-инструменте.

## Переустановить всё с нуля

```bash
pnpm reinstall
```

[`pnpm reinstall`](./structure/scripts/reinstall) — не способ обновления, а последнее средство, когда локальные зависимости сломались и ничего другое не помогло.

::: warning
Команда удаляет `node_modules` и лок-файл целиком и ставит всё с нуля: все транзитивные зависимости подтянутся в новых версиях разом, и что-то в проекте может сломаться так, что придётся искать причину и чинить. Перед коммитом обязательно проверьте diff `pnpm-lock.yaml`.
:::
