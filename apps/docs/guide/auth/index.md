# Авторизация

> **Ветки:** `auth-session` (сессии в памяти) и `postgres-prisma` (те же сессии, но в PostgreSQL через Prisma). Схема авторизации в обеих ветках одинаковая — различается только хранилище.

&nbsp;

## Выбор подхода

### Почему JWT access + refresh в HttpOnly куках

Существуют разные архитектурные подходы к аутентификации. Мы выбрали **JWT access token (15 мин) + refresh token с ротацией на сервере (in-memory)**.

| Подход                                              | Когда подходит                                                   | Почему не выбрали                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Сессионная кука** (nuxt-auth-utils, iron-session) | Монолит, простое приложение, не нужен logout на всех устройствах | Нельзя отозвать сессию мгновенно, нет истории устройств, нет reuse detection |
| **Чистый stateless JWT**                            | Микросервисы, service-to-service, очень короткий TTL             | JWT нельзя инвалидировать — украденный токен валиден до истечения            |
| **Managed auth** (Clerk, Auth0)                     | Стартап, нет требований к хранению данных                        | Внешняя зависимость, данные уходят третьей стороне, цена при масштабе        |
| **OAuth / OIDC** (Keycloak, Google)                 | B2B SaaS, корпоративный SSO                                      | Избыточно для шаблона; может быть добавлено поверх текущего решения          |
| **JWT access + refresh на сервере** ← наш выбор     | Nuxt/Next + отдельный API, нужна полная безопасность             | —                                                                            |

### Почему не stateless JWT

Stateless JWT не требует обращения к хранилищу сессий при каждом запросе — токен самодостаточен. Но у него фундаментальное ограничение: **токен нельзя инвалидировать досрочно**. Если токен украден или пользователь сменил пароль — токен остаётся валидным до истечения TTL.

Единственное решение — blacklist в Redis, что фактически делает JWT stateful, но сложнее.

### Почему не сессионная кука

Сессионная кука (вся сессия зашифрована в куке, без серверного хранилища) — простое решение, но не даёт:

- Принудительного logout: нельзя "отозвать" куку, которая уже у клиента
- Истории устройств: нет реестра сессий — нечего показывать
- Reuse detection: без записи на сервере невозможно определить повторное использование токена

### Наш выбор: гибрид

```
access_token  (JWT, 15 мин)            — проверка без обращения к хранилищу на каждый запрос
refresh_token (на сервере, 7 дней)     — обновление access_token, полный контроль над сессией
```

Это **де-факто стандарт** для веб-приложений с отдельным бэкендом: баланс между производительностью (обращение к серверному хранилищу сессий только раз в 15 минут) и безопасностью (refresh можно отозвать мгновенно, reuse detection, история сессий).

### Отличие от подхода в микросервисах

В микросервисной архитектуре JWT используется иначе:

```
Браузер → API Gateway → Service A (orders)
                      → Service B (payments)
                      → Service C (notifications)
```

Gateway проверяет JWT один раз на входе, каждый сервис получает уже верифицированный запрос. Refresh-токен живёт в централизованном Auth Service. Сервисы не трогают сессии вообще — это не их ответственность.

У нас один бэкенд, который сам управляет и access, и refresh токенами. Это правильно для монолита — переносить паттерн микросервисов сюда было бы избыточно.

## Почему не «только Nuxt»

Большинство Nuxt-приложений обходятся без отдельного бэкенда: Nitro сам обслуживает API, а авторизацию берёт на себя [nuxt-auth-utils](https://github.com/atinux/nuxt-auth-utils) с зашифрованной сессионной кукой. Это проще — одна кодовая база, один деплой, SSR тривиален (сервер уже знает пользователя, ничего пробрасывать не нужно).

**Почему здесь иначе:** в шаблоне NestJS владеет пользователями, паролями и сессиями. `nuxt-auth-utils` рассчитан на то, что владелец сессии — сам Nitro («This module only works with a Nuxt server running as it uses server API routes»). Подружить их означало бы держать сессию в двух местах — Nitro и NestJS — то есть завести два источника истины.

Когда какой подход уместен:

| Сценарий                                            | Кто владеет сессией                    |
| --------------------------------------------------- | -------------------------------------- |
| Fullstack Nuxt, БД прямо из Nitro                   | **Nitro** — `nuxt-auth-utils` идеален  |
| Внешний OAuth, данные в API Gateway                 | **Nitro** хранит токен провайдера      |
| Готовый провайдер (Auth0, Keycloak, Supabase)       | **провайдер**, Nitro только хранит     |
| Свой бэкенд с пользователями ← **наш случай**       | **бэкенд** (NestJS)                    |

Отдельный бэкенд оправдан, когда нужны: несколько клиентов (веб + мобильное приложение + партнёрское API), разделение фронт/бэк команд, серверная инфраструктура (cron, очереди, WebSocket, gRPC), или структура для большой кодовой базы (модули, DI, гварды).

**Цена этого выбора** — та самая сложность, которую описывают [Фронтенд](./frontend) и [Бэкенд](./backend): проброс кук через два хопа при SSR, silent refresh до рендера, дедупликация параллельных refresh. Всё это следствие того, что владелец сессии и рендерер — разные процессы.
