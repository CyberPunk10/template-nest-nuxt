# tsconfig.base.json

The repository holds seven TypeScript configs. One principle keeps them straight: **all but one exist only to check types**. Compilation is done by other tools — `nest build`, Nuxt, VitePress. The single exception is [`apps/backend/tsconfig.build.json`](./apps/backend/tsconfig-build).

## How inheritance works

```
template-nest-nuxt/
├── tsconfig.base.json          ← shared foundation
│
├── apps/
│   ├── backend/
│   │   ├── tsconfig.json
│   │   └── tsconfig.build.json ← extends the tsconfig.json above, not base
│   ├── frontend/
│   │   └── tsconfig.json
│   └── docs/
│       └── tsconfig.json
│
└── packages/
    ├── shared/
    │   └── tsconfig.json
    └── ui/
        └── tsconfig.json
```

Every config extends the base one except `apps/frontend`: its real configs are generated by Nuxt into `.nuxt/`, and the file itself only references them. The generated ones extend nothing either — Nuxt writes every option out in full, including the same `strict` and `noEmit` found here. [More detail](./apps/frontend/tsconfig).

Each file carries **only what makes it different** from the base. An option that isn't listed is inherited, and that's deliberate: repeating `strict` in every config is how you eventually get a package silently missing it.

## What the base holds

```json
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "noEmit": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

| Option | Why |
| --- | --- |
| `strict` | Full strictness, `strictNullChecks` included |
| `esModuleInterop` | Import CommonJS packages as `import x from` without `* as` |
| `forceConsistentCasingInFileNames` | Path casing: harmless on macOS, breaks the Docker build |
| `skipLibCheck` | Skip type-checking `node_modules` — faster, no third-party errors |
| `noEmit` | Produce nothing |
| `noImplicitOverride` | Overriding a method requires the `override` keyword |
| `noFallthroughCasesInSwitch` | Forbids falling through a `case` without `break` |

### Why `noEmit` lives in the base

Without it, any direct `tsc` run — by hand, from the IDE, from a tool that doesn't know better — scatters `.js` files next to the sources. The `type-check` script passes `--noEmit` as a flag, but protection that lives only in a command fails the moment the command isn't used.

The build config overrides it explicitly: `"noEmit": false`.

### Two checks beyond `strict`

`noImplicitOverride` and `noFallthroughCasesInSwitch` aren't part of `strict` — they're enabled separately.

The first requires marking an override explicitly:

```ts
class Child extends Base {
  handle() { }           // error
  override handle() { }  // correct
}
```

The point isn't ceremony: without it, it's easy to silently shadow a parent method while thinking you're writing a new one. The reverse case is worse — rename the method in the base class and the override in the subclass quietly stops being called.

The second catches a forgotten `break`:

```ts
switch (status) {
  case 'active':
    doSomething()      // error: falls through into 'archived'
  case 'archived':
    cleanup()
}
```

Deliberately grouped cases are still allowed — an empty `case` with no body isn't an error.

## What the base deliberately omits

### `paths` for `@repo/*`

Mapping workspace packages looks tempting:

```json
// don't
"paths": {
  "@repo/shared": ["./packages/shared/src/index.ts"]
}
```

It is both unnecessary and harmful. Unnecessary because pnpm symlinks packages into `node_modules/@repo/` and their `package.json` points `main` straight at `src/index.ts` — TypeScript finds them on its own. Harmful because `paths` points at **another package's sources**, so building the backend makes `tsc` try to compile them alongside it:

```
error TS6059: File '.../packages/shared/src/types/api.ts' is not under
rootDir '.../apps/backend/src'. 'rootDir' is expected to contain all source files.
```

Fixing that would mean resetting `"paths": {}` in the build config — a workaround that exists only to undo a setting you never needed.

### `module` and `moduleResolution`

These two describe how code is loaded at runtime — and the runtime differs per package, so there is no shared value.

| Package | Values | What loads the code |
| --- | --- | --- |
| `apps/backend` | `node16` | Node via `require` |
| `packages/shared`, `packages/ui`, `apps/docs` | `ESNext` + `bundler` | Vite, Rollup, VitePress |

Each package declares both options itself, side by side — they cannot drift apart by changing one and forgetting the other.

### `target` and `lib`

The backend runs on Node, the Vue packages in a browser. There is no shared value, so each config sets its own.

## The packages' configs

What each adds on top of the base:

| Config | Differences |
| --- | --- |
| [`apps/backend`](./apps/backend/tsconfig) | `node16` resolution, decorators, jest types |
| [`apps/backend/tsconfig.build.json`](./apps/backend/tsconfig-build) | the only one that compiles |

| [`apps/docs`](./apps/docs/tsconfig) | bundler resolution, DOM lib, VitePress types |

| [`packages/ui`](./packages/ui/tsconfig) | bundler resolution, DOM lib for components |

## Checking types

```bash
pnpm type-check
```

Walks every workspace, but the tool differs per package:

| Package | Command | Why |
| --- | --- | --- |
| `backend`, `shared` | `tsc --noEmit` | Plain TypeScript |
| `ui`, `docs` | `vue-tsc --noEmit` | `tsc` cannot parse `.vue` |
| `frontend` | `nuxt typecheck` | Needs the generated types from `.nuxt/` |
